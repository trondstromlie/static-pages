Getting Started

Intro

OpenCode is your AI-powered workspace. It sits between you and AI models like Claude, GPT, Gemini, or DeepSeek — managing context, tools, permissions, and actions so the model's reasoning turns into real, controlled work.

What is OpenCode?

The model does the thinking. OpenCode manages the context, tools, permissions, and actions needed to get work done.

  1. You define the goal.
  2. The model decides what to do.
  3. OpenCode executes the work safely.
  4. You review and approve the results.
Key ideaThe model decides what it wants to do. OpenCode controls and executes what's permitted. You remain accountable for scope, review, and approval.

How it works

Every request follows the same loop, end to end:

You send a request → OpenCode gathers context & tools → Reaches a model via a provider → Model reasons & may call tools → Tools execute the actions → Result flows back to you

Architecture diagram

Understanding tips

🧠 Build a mental model

Think of OpenCode as an agent loop: perceive → decide → act → observe → repeat.

🔧 Master the layers

Understand what each component is responsible for, and where to look when something goes wrong.

🎯 Follow the data flow

Trace a request end-to-end across components.

🧩 Learn by doing

Ask simple questions, inspect tool calls and outputs, try different providers.

📋 Debug effectively

Check permissions and tool availability; inspect session state and results.

💡 Best practices

Provide clear prompts and context. Keep sessions tidy. Prefer small, verifiable steps.

What makes a prompt good

Weak

"Find out how people currently do this, and summarize it for me."

Better

"This folder holds the interview transcript, the current process notes, and some examples. I want to understand what recurs, what conflicts, and where the current approach falls short. Back every finding with quotes."

Notice what's missing from the better version: no assigned role. Today's models read the role from the task and the context you give them. What makes the difference is the goal, the constraints, and giving the model real material to work from.

Setup

Before You Start

We don't spend time on installation once you're working with someone. Check that you can tick all five:

  • You have followed Gjensidige's internal setup guide.
  • You have a GitHub user with GitHub Copilot access — models run through your Copilot login.
  • OpenCode Desktop is installed and the app opens.
  • You are logged in and have confirmed that model access works.
  • You have opened the app at least once on your own.

Model Choice

Picking a Model

You choose the model yourself. Bigger models cost more of your monthly budget and are rarely better at simple tasks.

You askResponse style
"Hey, go do a thing."A fast, lightweight model: "OK, I'll go do the thing."
Same ask, mid-tier model"OK, but let me think about the best way to do the thing."
Same ask, top-tier model"Before we do the thing, are you sure it's the right thing to do?"

Bigger is not better, it's different. Pick the model for the task; the budget meter is why it matters.

Habits

Do's and Don'ts

Twelve lines that separate people who get value out of this from people who get frustrated.

Do
  • Start in plan mode, and read the proposal before you let it act
  • Give it your material first — context before question
  • Ask before you instruct. "What would you do here?" opens more than "do this"
  • Use your own vocabulary. Precise language steers the model
  • Ask for evidence: quotes, file names, where a claim comes from
  • Say what was wrong and why. Correcting beats starting over
Don't
  • Don't accept what you haven't read
  • Don't repeat the same prompt louder
  • Don't take a confident answer as a checked one
  • Don't reach for the biggest model by default
  • Don't paste real sensitive data
  • Don't build something on your own that another team owns
Safe and Within Bounds

The Rules That Apply

Data

  • The setup is what makes it safe, not the tool. Models run through Gjensidige's own agreement, on Gjensidige's terms.
  • Internal material belongs in the folder — the agent is meant to read it.
  • The approval does not travel. Same tool, different rules at home.
  • Real sensitive or customer data is the line that does not move.

Where the line is

  • You can experiment freely in safe test environments.
  • Anything with real production impact happens with the team that owns it.
  • Not knowing how to fix something yourself is not falling short.
Extend OpenCode

Skills

A skill is a packaged set of instructions (and optional scripts) that teaches an agent a specific piece of expertise. Install it once — it triggers automatically when relevant.

Install a skill

terminal
npx skills add https://github.com/vercel-labs/agent-skills --skill web-design-guidelines

This installs the web-design-guidelines skill from Vercel's open-source skill collection — it reviews UI code against 100+ best-practice rules: accessibility, focus states, forms, animation, typography, images, performance, dark mode, and touch/i18n handling.

Try it

prompt
Review this component against web design best practices.

What makes a good skill

  • Narrow, well-defined scope — one job, done thoroughly
  • Clear "use when" triggers, so the agent knows when to apply it
  • Instructions live in SKILL.md, not buried in a one-off prompt
  • Optional scripts/ and references/ extend it without bloating the core instructions
  • Versioned and shareable — the whole team benefits from one install

How to create good skills

  • Start from a real, repeated need — not a hypothetical one
  • Write SKILL.md as clear, direct instructions an agent can follow literally
  • Define explicit trigger phrases (e.g. "Review my UI", "Check accessibility")
  • Keep it focused — split unrelated expertise into separate skills
  • Test it on a real task before sharing it with others
TakeawaySkills turn one-off good prompting into reusable, shareable expertise anyone on the team can install.
Deep Dive

Skills Playbook

Skills give your AI reusable expertise. A closer look at what a skill actually is, what's inside one, and how to build a good one — written for designers, not developers.

What is a skill?

A skill is a reusable set of instructions that teaches an AI agent how to perform a particular type of work. You can think of it as:

  • A playbook the agent can follow
  • A way of packaging expert knowledge, standards, and best practices
  • Something you can use repeatedly instead of explaining the same process in every prompt
  • Something that can be personal, project-specific, or shared with others
🎨 Designer analogy

A prompt is like giving a designer feedback once. A skill is like giving the designer a design system, principles, examples, and a review checklist they can reuse.

💬 Key message

Prompts tell the agent what you want now. Skills teach the agent how you want this kind of work done repeatedly.

What's inside a skill?

At minimum, a skill contains a single file: SKILL.md. It can also contain supporting material:

folder structure
my-design-skill/
├── SKILL.md
├── references/
├── assets/
└── scripts/
  • SKILL.md — the actual playbook
  • references/ — principles, policies, research, or design-system documentation
  • assets/ — templates, examples, or reusable resources
  • scripts/ — automation for tasks that require repeatable execution

The Agent Skills specification only requires the SKILL.md file with metadata and Markdown instructions — the other folders are optional.

What the agent needs to understand

  • When should I use this skill?
  • What outcome should I create?
  • What steps should I follow?
  • Which rules and constraints apply?
  • How do I check my own work?

Example: web-design-guidelines

terminal
npx skills add https://github.com/vercel-labs/agent-skills --skill web-design-guidelines

This command adds the web-design-guidelines skill from the Vercel agent-skills repository. The skill is designed to review UI code against more than 100 web-interface rules covering accessibility, focus states, forms and error handling, animation, typography, images, performance, navigation and state, dark mode, touch interactions, and internationalization. It's intended for requests such as "Review my UI," "Check accessibility," or "Audit the UX."

Before the skill

"Review this interface and tell me if it is good."

The agent has to decide what "good" means.

After the skill

"Use the web-design-guidelines skill to review this interface. Prioritize accessibility and interaction issues. Explain each issue and suggest a concrete improvement."

Now the agent has a defined standard, a repeatable review method, shared terminology, and more consistent output.

Important distinctionThe skill does not replace the designer's judgment. It gives the designer and the agent a stronger shared starting point.

How to create a good skill — seven steps

1. Start with a repeated task

Choose something you or the squad explain to the agent repeatedly — e.g. reviewing a prototype for accessibility, turning research into evidence-based insights, checking design-system compliance, preparing an interview guide, critiquing a customer journey, or writing UX copy in Gjensidige's tone of voice.

RuleIf the task only happens once, it probably does not need to be a skill.

2. Define the outcome

Write down what the skill should produce. Instead of "Help with user research," use "Analyze user-research material and produce evidence-based themes, tensions, uncertainties, and research gaps." Ask: who will use the output? What decision should it support? What format should the agent create?

3. Describe when the skill should be used

The description acts like a label that helps the agent recognize the right moment to use the skill. A good description explains both what the skill does and when to use it, using specific keywords that help the agent match it to relevant work.

SKILL.md — frontmatter
---
name: research-synthesis
description: >
  Analyzes interviews and research notes to identify themes,
  tensions, evidence, contradictions, and research gaps.
  Use when synthesizing qualitative user research.
---

4. Write the workflow as clear steps

Give the agent a process, not just principles.

SKILL.md — workflow
## Workflow

1. Read all available research material.
2. Separate observations from interpretations.
3. Identify recurring themes and tensions.
4. Support every finding with evidence.
5. Mark contradictions and uncertainty.
6. Identify missing perspectives.
7. Produce the output using the required format.

For designers, a familiar structure could be: Understand → Plan → Build → Verify → Learn

  • Understand — read the context and identify what is known
  • Plan — explain the intended approach
  • Build — produce or modify the artifact
  • Verify — check it against principles and requirements
  • Learn — capture gaps and improvements for the next iteration

5. Add guardrails

Tell the agent what it must not do.

SKILL.md — guardrails
## Guardrails

- Do not invent user needs or research findings.
- Do not present assumptions as evidence.
- Do not jump directly to a solution.
- Do not ignore accessibility requirements.
- Ask for or identify missing context.

This is especially important in design work, where a polished output can otherwise hide weak evidence.

6. Add examples of good output

Examples clarify quality better than abstract instructions alone. Include one good example, one poor example, and a short explanation of the difference.

SKILL.md — example
## Good finding

Theme: Customers are uncertain about what happens next.

Evidence:
- "I submitted it, but I don't know whether anyone has seen it."
- "I expected some kind of confirmation."

Design implication:
Make claim status and the next expected step visible.

Uncertainty:
The evidence comes from two interviews and needs validation.

7. Add a verification checklist

A strong skill teaches the agent to review its own output.

SKILL.md — checklist
## Before completing the task, verify:

- Every finding is supported by evidence.
- Assumptions are clearly labelled.
- Accessibility has been considered.
- The output follows the requested format.
- Open questions and missing information are visible.
- The result supports a concrete design decision.

Then test the skill on a real task, inspect the output, and update the instructions. Skills should be maintained and improved through a learning loop — including learning from existing skills created by others.

What makes a skill good?

🎯 Specific

It solves a clearly defined type of task.

🏷️ Recognizable

The description clearly says when to use it.

📋 Procedural

It gives the agent an ordered workflow.

📚 Evidence-based

It identifies relevant sources and standards.

🚧 Bounded

It includes constraints and things not to do.

✅ Verifiable

It has a quality checklist.

♻️ Reusable

It works in more than one situation.

🌱 Maintainable

It can improve as the squad learns.

One-sentence summaryA good skill captures not only what an expert knows, but how that expert approaches, evaluates, and improves the work.

Modes & Reasoning

Agents

Match the setup to the task — which agent mode you use, and how much the model is asked to think, both change the outcome.

Agent modes

Plan Build Review Subagents
  • Plan — understand the problem and explore the approach, without changing anything
  • Build — implement an agreed solution
  • Review — identify bugs, risks, and unintended changes
  • Subagents — explore independent questions in parallel

Thinking effort

Low Default / Medium High Max
  • Low — small, explicit tasks
  • Default or medium — routine implementation
  • High — architecture and ambiguous problems
  • Maximum — complex decisions where mistakes are expensive
Recommended patternUse deeper reasoning for important decisions, then build incrementally.
Reference

Glossary

The words you'll meet most often, in plain language.

Model

The AI system that does the reasoning. OpenCode is not the model; it's what connects you to one.

Agent

A model working inside a loop, with tools and context, that can take multiple steps toward a goal.

Loop

The repeating cycle: think, act, observe, and think again — until finished or blocked.

Prompt

What you type or ask. Still matters, but far less than what the agent already has to work with.

Context

Everything the agent has access to when it responds. Nothing outside of it exists for the agent.

Token

The unit models process text in — roughly a word or part of a word.

Skill

An instruction file the agent reads before it starts, so a rule only has to be written once.

Harness

Everything set up around the model on your behalf: access, permissions, connections.

AGENTS.md

The note file the agent reads at the start of every session — a shared memory for the project.

Questions

FAQ

Do I need to know how to code?

No. You write in plain language, and the agent handles the technical part.

Do I need my own AI subscription?

No — access runs through your Gjensidige-issued GitHub Copilot login.

What does it cost me?

Nothing directly. Model use is budgeted centrally and tracked on Gjensidige's AI hub.

Which model should I pick?

Start with the default. Step up to a larger model when the task genuinely needs deeper reasoning.

What can I put into the models?

Internal work material is fine. Real sensitive or customer data is not.

What if I break something?

Every change the agent makes can be undone. Work in safe test environments while learning.

Is OpenCode open source?

Check current documentation for exact licensing details — your access is managed by Gjensidige.

Where do I get help?

Your chapter lead or team contact is the first stop for access and setup questions.
